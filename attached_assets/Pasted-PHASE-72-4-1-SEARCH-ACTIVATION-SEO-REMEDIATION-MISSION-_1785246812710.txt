C. SERVER-DELIVERED METADATA
==================================================

The current audit reports duplicated metadata because multiple SPA routes initially receive the same static server-delivered <head> before React hydration.

Implement deterministic server-delivered metadata for all audited public routes.

At minimum cover:

/
 /about-founder
 /founder
 /blog
 /guide
 /blog/:slug

Also inspect the sitemap and include every indexable public route audited by Phase 72.4.

Each indexable route must receive an appropriate server-delivered:

- <title>
- <meta name="description">
- <link rel="canonical">
- <meta property="og:title">
- <meta property="og:description">
- <meta property="og:image">
- <meta property="og:url">
- <meta name="twitter:card">
- <meta name="twitter:title">
- <meta name="twitter:description">
- <meta name="twitter:image">

Requirements:

1. Metadata must be present in the initial HTML response.

2. Do not depend exclusively on client-side Helmet hydration.

3. Retain Helmet for client-side navigation where useful.

4. Escape all dynamic metadata before insertion into HTML.

5. Never interpolate raw article HTML into <head>.

6. Use one reusable metadata resolver.

7. Use route-specific fallback metadata where database content is unavailable.

8. Blog article titles and descriptions must derive from authoritative stored article data.

9. Metadata must remain consistent between:
   - server-delivered HTML
   - React Helmet output
   - canonical URL
   - Open Graph URL
   - structured data URL

10. Do not introduce a heavy new SSR framework solely for this correction.

Prefer narrowly scoped server-side HTML-head injection compatible with the current Express/Vite production architecture.

E. SERVER-DELIVERED ARTICLE STRUCTURED DATA
==================================================

The Phase 72.4 audit reports Article schema missing on three expected blog pages.

Add server-delivered JSON-LD to every published blog article route.

Use:

@type: BlogPosting

unless an existing content type legitimately requires Article or NewsArticle.

Include applicable fields:

- @context
- @type
- @id
- headline
- description
- url
- mainEntityOfPage
- image
- datePublished
- dateModified
- author
- publisher
- articleSection
- keywords

Author:

{
  "@type": "Person",
  "name": "Oladele Oyeniyi",
  "url": "https://www.elevate360official.com/about-founder"
}

Publisher:

{
  "@type": "Organization",
  "name": "Elevate360Official",
  "url": "https://www.elevate360official.com/",
  "logo": {
    "@type": "ImageObject",
    "url": "<existing canonical crawlable brand-logo URL>"
  }
}

Requirements:

1. Use stored article values.

2. Do not fabricate:
   - dates
   - authors
   - images
   - keywords
   - sections

3. Omit optional fields when source data is absent.

4. Use ISO 8601 dates.

5. Use absolute crawlable image URLs.

6. Ensure headline and description match visible article content.

7. Safely serialize JSON-LD so content containing </script> cannot terminate the script block.

8. Avoid duplicate BlogPosting nodes after hydration.

9. Existing global Organization, Person and WebSite nodes must remain valid.

10. Add deterministic IDs, for example:

https://www.elevate360official.com/blog/<slug>#article

11. Add tests confirming schema exists in the initial HTML, not only after JavaScript execution.

F. LLMS.TXT
==================================================

Publish:

/llms.txt

The file must be:

- publicly accessible
- plain text or Markdown-compatible text
- served with an appropriate text content type
- concise
- factual
- stable
- free of private routes, credentials and internal instructions

# Elevate360Official

> Empowering Lives Through Technology & Words.

Include concise sections such as:

## About
## Primary Services
## Founder
## Key Resources
## Published Content
## Contact
## Policies

Use canonical absolute URLs.

Include only real, public, production resources.

At minimum, evaluate inclusion of:

- homepage
- about/founder page
- blog
- guide/resources
- publicly available service pages
- privacy policy
- terms
- contact page

Do not include:

- dashboard routes
- admin routes
- PIN routes
- API endpoints
- internal architecture
- environment-variable names
- database information
- private email addresses unless already intentionally public
- unsupported claims

Also determine whether the current robots.txt or routing configuration blocks /llms.txt.

It must not be blocked.

Important wording:

Do not describe llms.txt as an official search-engine ranking standard.

Do not claim guaranteed AI indexing, citation or agent compliance.

Describe it as a machine-readable discovery and orientation resource.
