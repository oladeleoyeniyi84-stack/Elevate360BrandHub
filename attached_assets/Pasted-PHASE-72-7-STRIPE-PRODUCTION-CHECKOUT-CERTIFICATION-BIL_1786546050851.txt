PRIMARY OBJECTIVE

Certify the Elevate360Official Stripe subscription transaction path from:

Customer account
→ checkout-session creation
→ Stripe-hosted Checkout
→ signed webhook
→ subscription synchronization
→ premium entitlement activation
→ account confirmation
→ billing portal
→ cancellation / downgrade

The result must provide objective evidence that a successful Stripe payment cannot leave the customer paid but unfulfilled, and that duplicate Stripe deliveries cannot improperly double-apply entitlements or credits.

⸻

A. CURRENT ARCHITECTURE — PRESERVE

The existing customer billing implementation already:

* requires authenticated customer identity for subscription checkout;
* validates paid tiers;
* validates Stripe configuration;
* resolves the Stripe price server-side;
* creates or reuses a Stripe Customer;
* creates a Stripe Checkout Session in subscription mode;
* attaches userId and tier metadata;
* uses client_reference_id;
* returns success to /account?billing=success;
* returns cancellation to /pricing?billing=cancelled;
* creates Billing Portal sessions server-side;
* processes subscription lifecycle events through the existing Stripe webhook infrastructure.

Do not introduce a second webhook endpoint.

Do not move sensitive Stripe operations into the browser.

D. WEBHOOK SIGNATURE CERTIFICATION

Inspect the existing:

POST /api/stripe/webhook

Confirm:

1. stripe-signature is required.
2. raw request body is used for signature verification.
3. parsed/re-serialized JSON is never substituted for the signed raw body.
4. STRIPE_WEBHOOK_SECRET is server-only.
5. malformed signatures return a controlled 400-class response.
6. unsigned webhook requests never reach fulfillment.
7. webhook errors return JSON.
8. webhook route cannot fall through to SPA HTML.
9. production logs never print secrets, payment method details, or raw request bodies.

Preserve the existing single webhook endpoint.

⸻

E. WEBHOOK EVENT IDEMPOTENCY — CRITICAL

Inspect whether Stripe EVENT-ID-level deduplication already exists.

Search for:

* processed_webhook_events
* stripe event id storage
* webhook event dedupe
* event.id
* idempotent webhook fulfillment

If robust Stripe event-level dedupe already exists:

* reuse it;
* test it;
* do not create a duplicate mechanism.

If it does NOT exist:

create an additive server-side persistence mechanism.

Preferred table:

stripe_processed_events

Suggested fields:

* event_id VARCHAR PRIMARY KEY
* event_type VARCHAR NOT NULL
* livemode BOOLEAN NOT NULL
* processed_at TIMESTAMP NOT NULL DEFAULT now()
* result VARCHAR
* metadata JSONB

Never store:

* card numbers
* payment-method payloads
* private customer objects
* webhook signature
* Stripe secret
* entire raw event payload

Required behavior:

1. Before business fulfillment, attempt atomic event claim.
2. Duplicate event.id must not re-apply premium credits or subscription fulfillment.
3. Mark processing outcome honestly.
4. Failed event handling must have a recoverable policy.
5. Avoid permanently claiming an event before recoverable processing if that would prevent a legitimate Stripe retry.

Architect must specifically review the claim/failure/retry transaction design.

If a new table is required, create:

scripts/create_phase72_7_tables.ts

It must be idempotent.

⸻

F. SUBSCRIPTION FULFILLMENT CERTIFICATION

Certify these Stripe events:

1. checkout.session.completed
2. customer.subscription.created
3. customer.subscription.updated
4. customer.subscription.deleted

For checkout.session.completed:

* ignore non-subscription sessions;
* resolve user only from trusted server/Stripe metadata;
* retrieve subscription from Stripe when required;
* synchronize subscription once;
* do not grant an unknown tier.

For subscription created/updated:

* validate tier mapping;
* apply premium entitlement only when subscription state is eligible;
* preserve existing active/trialing semantics unless architect identifies a bug.

For subscription deleted:

* update subscription state;
* remove premium entitlement appropriately;
* do not destroy customer/account history.

Unknown tier:

* must never partially write an invalid premium state;
* must not trigger infinite Stripe retries solely because metadata is unknown;
* must be logged in a redacted operational manner.

G. CREDIT / ENTITLEMENT DUPLICATION REVIEW

The current flow may receive multiple legitimate events for one subscription lifecycle.

Example:

checkout.session.completed
customer.subscription.created
customer.subscription.updated

Certify that these related events cannot improperly multiply:

* monthly AI credits;
* premium feature grants;
* entitlement records;
* subscription rows.

If applyTier(…, true) performs a top-up, carefully determine whether repeated lifecycle events can repeatedly top up the same customer.

This is a HIGH-PRIORITY architect review item.

Requirements:

* monthly credits must have an explicit renewal/activation idempotency boundary;
* duplicate webhooks must not duplicate credits;
* customer.subscription.updated events that contain no new billing period must not repeatedly grant monthly credit;
* renewal should grant credits once per eligible billing period if that is the intended commercial policy.

Do not silently alter the commercial credit policy.

Document the existing policy and any proposed correction.

J. ACCOUNT SUCCESS EXPERIENCE

Review the /account?billing=success behavior.

A query string alone must NOT be treated as proof that payment succeeded.

Requirements:

* billing=success may display a “Payment received / confirming subscription” UI state;
* authoritative premium status must come from the server/database;
* refresh premium status after Checkout return;
* handle brief webhook delay gracefully;
* do not display permanent “Premium active” solely because the URL contains billing=success;
* show a controlled pending state if Stripe completed Checkout but webhook fulfillment has not propagated yet.

Suggested UX:

“Payment received. We’re confirming your subscription.”

Then poll/refetch /api/premium/status with a tightly bounded retry window.

Stop when:

* premium becomes active; or
* timeout occurs.

Timeout copy:

“Your payment may still be processing. Refresh shortly or contact support if access is not updated.”

No infinite polling.
