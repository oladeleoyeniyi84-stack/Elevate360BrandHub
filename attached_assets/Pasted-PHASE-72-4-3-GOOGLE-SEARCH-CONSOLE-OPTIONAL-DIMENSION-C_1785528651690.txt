CURRENT CODE DEFECT

In server/services/googleSearchConsole.ts, the current dimension loop contains:

- country
- device
- searchAppearance

and requests every item as:

["date", dimension]

The returned error is stored in setErrors. The final status logic treats every setErrors entry as a genuine failure:

errorCount === 0
  ? "success"
  : importedAny
    ? "partial"
    : "error"

Therefore, a known unsupported optional dataset incorrectly downgrades an otherwise successful synchronization to PARTIAL.

PRIMARY OBJECTIVE

Correct the Search Console synchronization so that an unsupported searchAppearance grouping does not downgrade a successful core import.

CORE DATASETS

These remain required:

1. date + query
2. date + page
3. date + country
4. date + device
5. query + page

SEARCH APPEARANCE

searchAppearance is optional.

Do not request:

["date", "searchAppearance"]

because production has confirmed that Google rejects it for this property/API combination.

IMPLEMENTATION REQUIREMENTS

1. Separate required and optional dimension processing.

Required date-grouped dimensions:

- ["date", "country"]
- ["date", "device"]

Optional capability:

- searchAppearance

2. Do not fabricate dates.

The existing gsc_dimension_daily storage model is daily. Do not assign startDate, endDate, today's date, or another artificial date to non-date searchAppearance rows.

3. Avoid unnecessary schema changes.

If there is no truthful existing storage model for a non-date searchAppearance snapshot:

- do not add a migration merely to satisfy this corrective phase;
- do not persist fabricated daily rows;
- classify the capability as unsupported or unavailable;
- preserve that information as an operational note rather than a synchronization error.

4. Introduce a distinction between:

- blocking/core errors;
- optional unsupported capabilities;
- pagination truncation;
- informational notes.

A known unsupported searchAppearance combination must not be included in the error count used to determine success/partial/error.

5. Final status policy

SUCCESS:
- all required datasets complete successfully;
- optional searchAppearance is unsupported, absent, or returns no rows;
- no pagination cap is hit;
- no required dataset fails.

PARTIAL:
- at least one required dataset succeeds;
- another required dataset fails;
- or a required dataset hits the pagination cap;
- or another genuine non-optional integrity problem occurs.

ERROR:
- no required dataset is imported because of authentication, authorization, configuration, network, Google availability, or required-query failures.

NOT_CONFIGURED:
- preserve existing behavior unchanged.

6. Search-appearance behavior

Preferred safe behavior for this phase:

- remove searchAppearance from the date-grouped dimension loop;
- represent it as an optional unsupported capability for the current daily storage model;
- store an informational note such as:
  "Search appearance is unavailable as a daily grouped dimension for this property/API combination."
- do not place that note in errorText;
- do not mark the run partial solely because of that note.

If the current architecture already contains a truthful non-daily storage destination for searchAppearance, it may be queried separately as:

["searchAppearance"]

and stored there.

Do not create a new table or migration solely for this correction without first proving it is required.

7. Historical records

Do not rewrite or delete previous production sync rows.

Earlier ERROR and PARTIAL records are valid historical evidence.

The correction applies only to new sync runs.

8. Dashboard behavior

Update the Sync Status or operations display only as necessary so the newest run can distinguish:

- Success
- Partial
- Error
- Optional capability unavailable

Do not render the optional capability note as a red error.

Use neutral informational copy.

Suggested wording:

"Search appearance: unavailable for daily grouped import on this property."

Do not claim that Google does not support searchAppearance globally.

9. Preserve error honesty

Do not broadly suppress all HTTP 400 responses.

Only classify the confirmed unsupported-dimension case as optional when the response clearly identifies the searchAppearance dimension combination as invalid.

Other 400 responses must remain visible as genuine failures.

10. Preserve security

- Do not expose access tokens.
- Do not expose private keys.
- Preserve error redaction.
- Preserve credential parsing.
- Preserve the server-side trust boundary.
- Preserve the founder PIN requirement.
- Do not add client-controlled sync status fields.
